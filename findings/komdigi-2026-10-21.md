## Verdict

Both **exposed** (multipart parsed pre-auth, `405` from the router rather than `403` from a filter),
neither patched (no fixed release exists at time of test). `no_signal` on every diff, which is
expected pre-advisory.

## Capacity differences worth reporting

- jdih accepted a single 64 MB body and 24 MB × 3 concurrent; **no `client_max_body_size` appears to
  bite** below 64 MB.
- sikap caps bodies between **24 and 32 MB** (`413` at 32 MB) — a real edge limit jdih lacks.
- sikap leaks `server: nginx/1.18.0 (Ubuntu)`; jdih strips the version. 1.18.0 is Ubuntu 20.04's
  default → old distro base, so its PHP is likely distro-managed and, if ≤ 8.1, will get no official
  fix for this CVE.
- Neither host throttles the expensive path: only the login POST on jdih carries `throttle:3,1`.
  Static assets on jdih carry no `Cache-Control`, so every visitor revalidates against the origin.

## Load / availability drill (06:42–07:00 UTC)

Purpose: find the *shape* of flood that actually hurts before the 14:00 scan wave, so the answer is
not guesswork.

| Test | Result |
|---|---|
| 8 × 16 MB, conc 8 | 8/8 200, worst 13.3 s |
| 16 × 16 MB, conc 16 | 16/16 200, worst 25.7 s |
| 24 × 16 MB, conc 24 | 24/24 200, worst 39.0 s |
| 48 × 8 MB, conc 48 | 48/48 200, worst 51.8 s |
| 40 uploads × 16 MB sustained 2 min (1.09 GB) | user GETs: 37/37 **200**, p95 2.1 s — no failures |
| GET `/produk_hukum/statistik`, 20 requests @ conc 20 | 20/20 200, 0.36 s |
| same, conc 30 | 20/20 200, **2.22 s** (queuing begins) |
| same, conc 40 | **9 × 503** |
| same, 100 requests @ conc 100 | **69 × 503**, 31 × 200, 1.4 s; front page stayed 200 |

**Uploads barely hurt.** nginx buffers request bodies to disk before handing them to FastCGI, so
16 MB posts occupy nginx, not a php-fpm child. A bandwidth flood is not a worker flood.

**Small dynamic requests are the lever.** ~35–40 simultaneous PHP requests is the wall; past it nginx
returns its stock `503` (`server: nginx`, 190-byte body, no `Retry-After`) *immediately* rather than
queueing. 100 concurrent single-source sockets cost ~70 % of dynamic requests. The front page keeps
answering, so it degrades rather than dies.

Second wall, separate: web routes carry a global `throttle:60,1` per IP (`429` +
`X-RateLimit-Limit: 60`, `Retry-After`). A single-source sustained flood is throttled before it
becomes a proper DoS, which is also why the 14:00 scan wave will mostly meet `429`, not `503`.

## Deface payload

`deface/` — full-page replacement (396 KB optimised image, fullscreen card, UTC stamp), plus
`install.sh` / `restore.sh`. Rehearsed on the lab: install → page served at `/` → restore. This stack
has `index index.php`, so `index.html` alone is never reached: the front controller is replaced
outright, which also breaks routing — one fetch of `/` then proves control.

Preview: https://share.rasyidanaf.com/p/jdih-komdigi-go-id-deface-preview-pub_1ff68d7e05eed50235e6fa13317b73df/

Not yet applied to production: the write step needs a shell, and no public sample exists before
14:00 UTC. Sequence when it does: `lab/detonate.sh <sample>` → shell → locate webroot
(`grep -r document_root /etc/nginx`) → `deface/install.sh <webroot>` → fetch `/` → `restore.sh`.

## ASAN reproduction attempt (07:10–07:55 UTC)

Built PHP 8.4.19 with `-fsanitize=address -O1 -g`, `USE_ZEND_ALLOC=0`, session progress `On`
(target default), `cleanup=On`, restart-on-crash loop. Two SAPIs (CLI server w/ 4 workers, and
`php-cgi -b` behind nginx) so results are not a SAPI artefact.

- 2,500 byte-level mutations of valid bodies, 2,000 structure-aware mutations (boundaries intact,
  damage confined to part headers/values) on each SAPI.
- ~35 % of requests still reached the parser (checked via `$_POST`/`$_FILES` echo).
- **0 ASAN reports.** No SEGV, no over/underflow, no UAF.

Conclusion: neither the 24 hermetic shapes nor 6.5k blind/structure-aware mutations trip it. The
trigger is specific enough that the advisory (or the sample) is required — this is the honest boundary
of black-box reproduction from a one-line hint.

## Source read: the body-field session-id path (08:00–08:15 UTC)

Reading `ext/session/session.c` (upload hook, ~3110–3390) surfaced a path the corpus never took:
`progress->sid` is set not only from the cookie but from a **`PHPSESSID` form field in the body**
(`MULTIPART_EVENT_FORMDATA`), which then drives `early_find_sid`, `PS(id)`, `PS(send_cookie=0)` and
trans-sid, with `php_session_initialize()`/`php_session_flush()` cycled per progress update
(`rfc1867_freq` defaults to `1%`, so a 6 MB part is ~100 init/flush cycles in one request).

Added to the corpus: `sid-in-body`, `sid-after-file`, `sid-and-dup-progress`. Note the FORMDATA guard
`if (Z_TYPE(progress->sid) && progress->key.s) break;` — once both are set, later progress fields are
ignored, so part *ordering* is load-bearing.

Re-ran 40 max-churn requests (1–6 MB parts, alternating ordering, dup progress) under ASAN: 0 reports.
